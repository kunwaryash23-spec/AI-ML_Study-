### 2. The blog search app — you built a graph and then didn't use it

This is the substantial work of the day, so it gets the most space.

**What you built.** A four-node LangGraph with a cycle:

```
START → agent ──(tools_condition)──> retrieve ──(grade_documents)──> generate → END
          ↑                                            │
          └────────────── rewrite ←────────────────────┘
```

- `agent` decides whether to call the retriever at all.
- `retrieve` is a `ToolNode` wrapping `create_retriever_tool(...)` over Qdrant.
- `grade_documents` is a **conditional edge**, not a node — it asks a `temperature=0` model for a binary `yes`/`no` on whether the retrieved chunks are relevant, using `with_structured_output(grade)` against a one-field Pydantic model.
- On `no`, `rewrite` rephrases the question and sends it back to `agent`. On `yes`, `generate` answers with the `rlm/rag-prompt` from LangChain Hub.

**This is Corrective RAG.** It has a name, it's a real published pattern, and you implemented it correctly. The design instinct behind it is the one worth keeping: *a retrieval system should be allowed to notice it retrieved garbage and try again.* Every RAG pipeline you have written before this one — Days 23 through 33 — retrieves once and answers, right or wrong. This is the first that can say "that's not relevant" and loop.

**Now the problem.** In `main()`:

```python
graph = get_graph(retriever_tool)          # built...
...
inputs = {"messages": [HumanMessage(content=query)]}   # ...inputs prepared...
...
response = answer_query(retriever, query)  # ...and neither one is used.
st.write(response)
```

`answer_query()` is a straight retrieve-then-prompt chain. No agent, no grader, no rewrite loop. **Every line of graph code in that file is dead.** `get_graph`, `agent`, `grade_documents`, `rewrite`, `generate`, `generate_message`, `AgentState` — none of it executes.

The fix is one line:

```python
response = generate_message(graph, inputs)
```

**Why this is worth more than a one-line fix.** This is the classic shape of a debugging session that ends badly: the graph didn't work, so you wrote a simple path that did work, put it next to the broken one, and shipped. Understandable — and the app does answer questions. But now the file contains 200 lines that *look* like they run and don't, and in three weeks you will read `grade_documents` and believe your app grades documents.

Two habits that prevent this:

1. **When you write a fallback, mark it.** `# FALLBACK: graph path disabled 2026-08-27, agent returned empty content` costs five seconds and saves the misreading entirely.
2. **When the graph path fails, print the failure instead of routing around it.** `generate_message` swallows a lot: it iterates `graph.stream()`, keeps only the last message, and returns `""` if nothing matched. Wrap the call in a `try` and `st.exception(e)` — a Streamlit app that shows you the traceback is worth ten that show a blank box.

**Two smaller things in the same file:**

- **`from http import client` (line 1).** Almost certainly an editor autocomplete accident. It is shadowed later by the local `client = QdrantClient(...)`, so it does nothing — but it is the kind of stray import that makes a reader wonder what HTTP client you're using. Delete it.
- **`generate` returns a raw string into a message channel.** `return {"messages": [response]}` where `response` is a `str` from `StrOutputParser()`. `add_messages` will coerce it, but every other node returns a proper message object. Consistency here will matter when you start filtering on message type.
- **Verify `gemini-3.5-flash` is a real model id** before debugging anything else in this app. It appears five times. If the string is wrong, every node fails identically and the symptom looks like a graph problem rather than a name problem.

**On Qdrant.** This is your third vector store — Chroma (Days 31–33), hand-rolled cosine (Days 23–26), now Qdrant Cloud. The meaningful difference here is that Qdrant is *remote*: `chroma_db/` was a folder on your disk, this is a cluster behind a URL and an API key, with a `timeout=120` because the round trip is real. That is the shift from a local index to a service, and it's the version that survives contact with a deployed app.

This is the third consecutive sync where a key arrived inline, and the second time a key was put *back* into a file after being moved to `os.getenv()`. The pattern is clear enough to name: **the key gets pasted in while you are debugging, because `os.getenv()` returns `None` when `.env` isn't loaded and you want to rule that out.** The fix is not willpower, it's making the env path work the first time. Put this at the top of every notebook, above every other import:

```python

import os
assert os.getenv("GOOGLE_API_KEY"), "GOOGLE_API_KEY missing — copy .env.example to .env"
```

The `assert` is the point. It fails loudly with an instruction, at line 3, instead of failing obscurely 40 lines later — which is the moment you reach for the literal.
