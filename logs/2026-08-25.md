### 1. Tool calling — the agent loop, built twice

`Day_33/tool_calling_agent.ipynb` (15 cells, new)

**The structure of this notebook is the best thing about it.** Cell 4 hand-rolls the agent loop with a hard-coded plan:

Writing the dumb version first is exactly right. `create_agent` is now a black box that replaces one specific thing you already understand — the `decide → act → observe` loop — instead of being magic. **Keep doing this with every new abstraction.** The comment you left, *"A real agent asks an LLM 'what next?' each step. We hard-code 2 steps here,"* is the whole lesson in one line.

**The docstring is the API.** This is the part beginners miss for months:

```python
@tool
def calculator(expression: str) -> float:
    """Evaluate an arithmetic expression, e.g. '9 * 10'."""
```

That docstring is not documentation for you. It is the *only* thing the model sees when deciding whether to reach for this tool, and the type hints are what become the JSON schema for the arguments. A vague docstring is a bug — the model will either skip a tool it should have used or call it with garbage. Yours includes a concrete example, which measurably improves selection. Treat tool docstrings as prompt engineering, because that is what they are.

#### `safe_eval` — and the cell that proves why it exists

Cell 2 builds an AST-whitelist evaluator: parse the expression, walk the tree, and only execute nodes whose operator is in `_OPS`. Anything else raises. Eight allowed operations, nothing more.

```python
def calculator(expression: str) -> float:
    return safe_eval(expression)      # never eval() model input
```

Then cell 14:

```python
user_input = input("pls enter your input: ")
result = eval(user_input)
```

...and you typed `os.system('ls')`, and it printed your entire directory. **That is arbitrary code execution, demonstrated on yourself, in your own notebook.** Nobody who has watched that happen forgets it. `os.system('ls')` is the harmless version; `__import__('os').system('rm -rf ~')` is the same keystrokes with a worse verb, and an LLM that has been prompt-injected by text inside a PDF you retrieved will happily produce the second one.

Put a markdown cell between them saying *"cell 2 is the fix for cell 14"* so the pairing survives you forgetting the context. **The rule this teaches, and it generalizes far past `eval`: never hand model output or user input to an interpreter.** You applied the same rule again on Day 34 with parameterized SQL — that consistency is not an accident, it's the beginning of a security instinct.

#### Human-in-the-loop, and where it leaks

```python
@tool
def delete_file(path: str) -> str:
    """Delete a file. Requires human confirmation."""
    answer = input(f"Approve deleting '{path}'? [y/N] ")
    if answer.lower() != "y":
        return "Denied by human."
```

Gating a destructive tool behind explicit approval is the right instinct and most people don't reach for it this early. Defaulting to `N` is right too. **Three gaps to know about, in order of how much they matter:**

1. **"Denied by human." goes back to the model as a normal tool result.** The model can read it, decide you misunderstood, and call `delete_file` again — possibly with a slightly different path. A denial should terminate the turn, not become another observation in the loop. Raising an exception and catching it outside `agent.invoke` is the crude fix; LangGraph's `interrupt()` is the real one, and it's the natural next thing to learn here.
2. **`input()` requires a human at a terminal.** The moment this agent runs in a FastAPI handler or a scheduled job there is no stdin, and `input()` either blocks forever or raises `EOFError`. Approval has to be a *state the graph pauses in*, not a blocking call inside a function.
3. **No path validation.** `delete_file("../../.env")` is a valid call. Any tool that touches the filesystem needs to resolve the path and assert it stays inside an allowed root:

```python
root = Path("D:/Ai engineering course").resolve()
target = (root / path).resolve()
if not target.is_relative_to(root):
    return "Refused: path outside the allowed directory."
```

**Also:** `recursion_limit=10` in cell 8 is a genuinely important guard — without it, a model that keeps calling the same tool loops until your quota dies. Your comments label it *"guard #1"* and the logging *"guard #4"*, but guards 2 and 3 never appear in the notebook. Either write them (per-tool timeout, and an output-size cap so a tool can't return 400 KB into the context window) or renumber. And the `verified` decorator in cell 3 is defined and never used — it also has a bug, since `tool_fn.invoke(kwargs or args)` will pass a tuple where LangChain expects a dict. Wire it up properly or delete it; dead code in a notebook reads as "this works," and it doesn't.

### 2. Agentic RAG — persistence and citations, but the retrieval isn't landing

`Day_33/Agentic_RAG.ipynb` (5 cells, new)

**Three real upgrades over Day 31–32.**

**`PersistentClient(path=DB_PATH)`.** The index is written to disk and survives a kernel restart. Cell 3 opens the existing collection instead of rebuilding it — you left a comment saying exactly that. Embedding is the expensive step in RAG; not repeating it is the whole point.

**You took the sentence-embeddings advice from last sync.** Passing `documents=` with no `embeddings=` lets Chroma run `all-MiniLM-L6-v2` itself. That is the swap the 2026-08-24 log flagged as the highest-value experiment available, and it's now the default path in this notebook.

**Page numbers as metadata.**

```python
metas.append({"page": page_no})
ids.append(f"p{page_no}-c{j}")
```

This is how you get citations. An answer that says *"according to page 7"* is verifiable; one that doesn't is a claim you have to take on faith. Carrying provenance through chunking is a habit worth having permanently, and stable `p7-c2`-style ids mean a re-run overwrites rather than duplicates.

#### But look at what came back

```
[page 19] . Vet. Behav. Clin. Appl. Res. 2008, 3, 74-86. [CrossRef]
96. Fox, R.; Gee, N.R. Great Expectations: ...
[page 17] equency of Marking. J. Am. Vet. Med. Assoc. 2001, 219, 1709-1713.
```

The query was *"what is this document about"* and the top two hits are **the bibliography**. And `search_pdf("what should I improve")` scored 0.175 and 0.077 on a demographics table. Both are retrieval failures, and the causes are worth separating because only one is your code's fault:

- **The bibliography problem is fixable and it's the big one.** In a 19-page academic paper, pages 15–19 are references — dense, high-entropy, semantically meaningless text that embeds *near everything* because it shares vocabulary with the whole field. They are pure noise and they are crowding out real content. Drop them at ingest: cut at the page where "References" first appears, or filter chunks where the citation-bracket density is high. Removing the references alone will visibly move your scores.
- **`"what should I improve"` is not a question this document can answer.** It's about *you*, not about dog and cat management. Zero-ish similarity is the correct response; the failure is that Chroma returns the top-k regardless. **Add a score floor** — if the best hit is below ~0.3, return "nothing relevant found" rather than three bad chunks. An agent handed three irrelevant chunks will confidently hallucinate an answer out of them. A retriever that can say *"I don't have this"* is worth more than one that always answers.
- **Chunking resets at every page boundary.** `chunk()` is called per page, so a paragraph spanning pages 6–7 gets cut in half and the `OVERLAP=200` never bridges it. Join the page text first, keep a running character offset, and map each chunk back to a page from that offset.

**Two structural notes.** Cell 3 rebuilds `CHUNKS` and `METAS` by re-reading and re-chunking the whole PDF, when the collection on disk already holds all of it — `collection.get()` returns the same thing without touching the file. And the hand-written `SEARCH_TOOL` JSON schema is genuinely worth having written once, because it shows you what `@tool` generates for you — but **this notebook never actually gives that tool to a model.** Cell 4 is empty. You already have a working `create_agent` in the other Day 33 notebook; connecting them is about ten lines and turns this from "a retriever with a schema next to it" into the agentic RAG the filename promises. **That's the highest-value next thing in the repo.**

### 3. Two kinds of memory, and why conflating them causes bugs

`Day_34/agent_with_memory.ipynb` (17 cells, new)

The notebook implements two mechanisms that are both called "memory" and are not the same thing. Naming the difference is the main lesson here:

| | Thread checkpointer | SQLite notes table |
|---|---|---|
| What it stores | The whole message history | Individual facts the user asked to keep |
| Who decides | Automatic, every turn | The model, by calling `save_note` |
| Scope | One `thread_id` | Global, all threads |
| Survives restart | ❌ `InMemorySaver` is RAM | ✅ it's a file on disk |
| Analogy | Short-term / episodic | Long-term / semantic |

```python
assistant = create_agent(model, tools=TOOLS, checkpointer=InMemorySaver())
me = {"configurable": {"thread_id": "another_thread_test"}}
```

The `thread_id` is the key the checkpointer files history under — and it's why the commented-out demo in cell 3 works: *"My name is Bishal"* then *"What is my name?"* recalls it, because both calls carried the same config. Change the `thread_id` and the agent has amnesia. **That is the mechanism behind every "new chat" button you've ever clicked.** Swap `InMemorySaver` for `SqliteSaver` and conversations survive a restart too.

**Parameterized SQL throughout.** `conn.execute("INSERT INTO notes (text) VALUES (?)", (text,))` — placeholders, not f-strings. The `text` here comes from an LLM, which got it from a user, and an f-string would make `'); DROP TABLE notes; --` a working attack. Same rule as `safe_eval` on Day 33, different interpreter. Two for two.

**`delete_all_notes` is deliberately not a `@tool`.** It's a plain function you call yourself. Correct, and worth stating as a principle: *a tool that is both destructive and unbounded should not be in the tool list at all.* Not gated — absent. The model cannot misuse a capability it was never given.

#### The broken contract

`list_notes()` returns **only the text**:

```python
notes = [row[0] for row in cursor.fetchall()]   # SELECT text
return "; ".join(notes) or "(nothing saved yet)"
```

But `delete_note(note_id: int)` needs an **id**. So the agent can list notes all day and still have no way to learn the id of the one it should delete. Look at what you actually had to type in cell 10:

```python
say(me, "delete the note that has id 6 ")
```

You supplied the id by hand, from outside the system. The agent could never have found it. **Tools have to compose — the output of one has to be a valid input to the next.** One-line fix:

```python
cursor = conn.execute("SELECT id, text FROM notes ORDER BY id ASC")
return "; ".join(f"{i}: {t}" for i, t in cursor.fetchall()) or "(nothing saved yet)"
```

Now `list_notes` → *"5: ram is a good boy"* → the model reads `5` → `delete_note(5)`. This "does the output of tool A feed tool B?" check is one of the most useful things to run over any tool set before handing it to a model.

#### The outputs no longer tell the truth

Cell 14 runs `delete_all_notes()` and returns `'all notes deleted'`. Cell 15 then lists ids and returns `[5, 6]`. Both outputs are saved in the file, and together they're impossible — a table cannot be empty and contain rows 5 and 6. **The cells were run out of order**, so the saved trace is fiction.

This matters more than it looks. Notebook state is invisible: what you see is the output of whenever a cell last ran, not what would happen if you ran the file top to bottom. **Restart & Run All before saving anything you intend to keep or commit.** If it doesn't survive that, it isn't reproducible, and a notebook you can't reproduce is a note, not a result.

Related footgun in the same notebook: cells 11 and 15 redefine `list_notes` as a *plain function*, shadowing the `@tool`-decorated one in the global namespace. `TOOLS` was built in cell 10 and holds a reference to the real tool object, so nothing broke this time — but rebuild `TOOLS` after cell 11 and you'd pass a bare function where LangChain expects a `BaseTool`, and the error message would not point you here. Give debug copies a different name (`_peek_notes`).

Cells 1, 5, 6, 9 are empty. Clear them out.
