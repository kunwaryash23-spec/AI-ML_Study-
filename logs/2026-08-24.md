### 1. `Network` — the MLP becomes a class

`Notebooks/MNIST_Network_Class.ipynb` (18 cells, new)

Four layers, `784 → 256 → 128 → 64 → 10`, all inside one `nn.Sequential` attribute, plus `fit()`, `predict()` and `score()` methods. It trained cleanly:

```
epoch 1/8  loss 0.4100
...
epoch 8/8  loss 0.0288

train acc: 0.9918
test  acc: 0.9740      # 364 wrong out of 14,000
```

**Four things in this notebook show real understanding, and they're worth naming so you keep doing them.**

1. **You named the method `fit()`, not `train()` — and you wrote down why.** `nn.Module` already owns `.train()`; it's the mode switch that turns dropout and batchnorm on. Overriding it would have broken your own `self.train()` / `self.eval()` calls from the inside, and the failure would have been silent — no exception, just a model evaluating in the wrong mode. Matching scikit-learn's `fit`/`predict`/`score` naming on top of that is exactly right: anyone who knows sklearn can now use your class without reading it.

2. **No softmax on the last layer.** `nn.CrossEntropyLoss` applies log-softmax internally. Adding your own would squash the logits twice and flatten the gradients. This is the most common PyTorch beginner bug and you avoided it deliberately.

3. **`@torch.no_grad()` on `predict` and `score`, with `self.eval()` inside.** Both halves matter and they do different jobs — `no_grad` stops the autograd graph from being built (memory + speed), `eval()` flips module behaviour. You batched inference at 512 too, so a 14,000-row `predict` doesn't try to allocate one giant activation tensor.

4. **`running += loss.item() * len(idx)`.** The last batch of 56,000 at `batch_size=128` has 96 rows, not 128. A plain mean-of-means would quietly overweight it. Weighting by actual batch size and dividing by `n` gives the true epoch loss. Small detail, and most tutorials get it wrong.

**The gap worth closing next.** You're reading `train acc: 0.9918` vs `test acc: 0.9740` off two printed numbers at the end of training. That tells you overfitting *happened* but not *when*. Add a validation split and append val-loss to `self.history` alongside train-loss each epoch:

```python
self.history.append({"train": epoch_loss, "val": val_loss})
```

Then plot both curves. The epoch where val-loss turns upward while train-loss keeps falling is the moment you should have stopped — and seeing that divergence with your own eyes is what makes early stopping click. Right now `self.history` holds one number per epoch and the plot can only ever show you half the story.

**Also worth knowing:** 97.4% on MNIST is a solid MLP result, and it is roughly the ceiling for this architecture. A CNN gets 99%+ on the same data. The reason is instructive — `X.reshape(-1, 784)` throws away the fact that pixel 100 and pixel 128 are vertically adjacent. Your MLP has to learn spatial structure from scratch; a conv layer is handed it for free. That 2-point gap is the entire argument for convolutions, and you now have a baseline to measure it against.

### 2. `Retriever` — the RAG pipeline becomes a class

`Notebooks/Retriever_Class.ipynb` (11 cells, new)

`chunker() → embedder() → search()`, with `self.chunks` and `self.vectorizer` carried between them. Verified on a small hand-written document first (5 chunks, 98-word vocabulary) and then on `Day_25/Micro_Syallabus.pdf` without changing a line of the class.

**The single most important line in the whole notebook:**

```python
query_vector = self.vectorizer.transform([query]).toarray()[0]
```

`.transform()`, not `.fit_transform()`. Back on 2026-08-21 the Day 31 version called `fit_transform` inside the embed helper, which refit the vectorizer on every query and returned nothing useful. You've now fixed it in the structurally correct way: fit once in `embedder()`, store the fitted vectorizer on `self`, transform-only afterwards. **A TF-IDF vector is only meaningful relative to the vocabulary it was fitted on** — the query and the chunks have to be translated by the same dictionary or the comparison is nonsense.

**You also fixed the `n_components=2` bug from last sync — by deletion.** The Day 31 notebook pushed 287 chunks through `TruncatedSVD(n_components=2)`, collapsing everything into a 2-D plane where unrelated chunks land on top of each other. The `Retriever` class drops SVD entirely and indexes raw TF-IDF. That is the right call at this stage: fewer moving parts, and the retrieval results in cell 7 are visibly sensible — *"how are the vectors compared to each other?"* correctly returns the cosine-similarity chunk at 0.265.

**Three more good defensive choices:**

- `delete_collection()` in a `try/except` before `create_collection()`. Re-running an embed cell in a notebook is the #1 way to end up with duplicated documents in a vector store. You handled it.
- `if not query_vector.any()` — the all-zero query guard. If a question uses no word that appears in the document, TF-IDF returns a zero vector and cosine distance against it is mathematically undefined. Chroma would have returned garbage rather than raising. Catching this yourself is a mature instinct.
- `if self.overlap >= self.chunk_size: raise ValueError`. Without it, `start += chunk_size - overlap` never advances and `chunker()` hangs forever. Turning an infinite loop into an immediate error is exactly what a constructor guard is for.

**Notice what those scores are telling you, though.** Your best hit on the PDF scored **0.288**, and the top result for *"what is covered in the course?"* was the FAQ paragraph about **cost and payment**. That is a retrieval failure, and it's not a bug in your code — it's TF-IDF's ceiling. TF-IDF matches *words*. The question says "covered", the syllabus says "SKILLS & TOOLS YOU WILL MASTER" — zero shared vocabulary, so zero similarity, no matter how obviously related they are to a human.

This is precisely the wall that sentence embeddings exist to break. Swapping the body of `embedder()` for:

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("all-MiniLM-L6-v2")
embeddings = model.encode(self.chunks)
```

...is about four lines, and `search()` doesn't change at all. **That is the payoff for having written this as a class**: the embedding strategy is now one swappable method rather than a rewrite. Run both against the same three questions and keep the score comparison — it's the cleanest demonstration you'll get of why the field moved from lexical to dense retrieval.

**`Notebooks/RAG_metadata_debug.ipynb`** — `RateLimitError: 429, quota exceeded`. Not a code bug; the free Gemini tier ran out. The idea in it is genuinely good: have an LLM label every chunk with a topic from a fixed list, store those as Chroma metadata, then filter with `search(..., where={"topic": "RAG"})` to narrow the search space before similarity ranking. Two things that made it well-built:

- `response_format={"type": "json_object"}` plus `temperature=0` — structured output, deterministic. Right way to call an LLM for a data-processing step.

One structural problem to fix before re-running: it sends **all chunks in a single request** and expects one item back per chunk, in order. On a long PDF that will blow the context window or silently return a short list, and `zip(chunks, metadatas)` will then truncate without complaint.
